## Episode 1 — phone "could not connect": IPv4 vs IPv6 port conflict

**Symptom.** The Look tab failed on the phone, and on the Mac `http://localhost:3001/health` returned **Grafana HTML**, not our backend.

```
backend: ALREADY RUNNING
<!DOCTYPE html> ... <title>Grafana</title> ...
```

**Cause (verified).** `lsof` showed two processes LISTENing on 3001 at once:

```
bun        6559  ... TCP *:3001 (LISTEN)        # our backend (IPv4)
com.docke 16261  ... TCP [::]:3001 (LISTEN)     # Docker (Grafana container) (IPv6)
```

`localhost` resolves IPv6 (`::1`) first, so it hit Docker/Grafana. When the phone reached `.local:3001` and it resolved over IPv6, it landed on Grafana and broke.

**Fix.** Moved our backend off the contested port: `backend/.env` `PORT=3001 → 8787`, and `ios-app/project.yml` `BackendBaseURL` to `:8787`. Left Grafana (Docker) untouched.

**Lesson.** One port number can have *separate* IPv4 and IPv6 bindings. Because of `localhost` resolution order (usually IPv6 first), you can "start your server" and still get someone else's response. Always check what holds a host port with `lsof -nP -iTCP:<port> -sTCP:LISTEN`.

## Episode 2 — containerization: the Dockerfile and excluding secrets

Before deploying, package the app as a "box that runs identically anywhere." Two key files:

- `backend/Dockerfile` — `oven/bun:1-slim` base, copy deps manifest first then `bun install` (layer cache), copy source, `ENV PORT=8080`, `CMD ["bun","src/index.ts"]`.
- `backend/.dockerignore` — **excludes `.env` (secrets) from the image.** Keys are injected as runtime env vars, never baked into the image.

**Lesson.** Image = frozen template, container = a running instance of it, Dockerfile = the recipe. Copy the dependency manifest *before* the source so that when only source changes, `install` is cached and builds stay fast. Never put secrets in the image or git.

## Episode 3 — the "Up but health fails" trap

**Symptom.** After `docker run`, `curl /health` from the host failed, yet `docker logs` was **empty** and `docker ps` showed the container **Up**. No crash, but no response — a contradiction.

**Cause (verified).** Poking from *inside* the container with `bun -e 'fetch(...)'` returned a healthy response, and the logs did contain `Server running at http://localhost:8080`. So the server was fine; the *verification* was the bug:
- `curl --retry-connrefused` only retries on "connection refused." But Docker's port proxy opens the host port *immediately*, so while the app is still booting you get a **connection reset**, not "refused" → the retries never engaged and it gave up before the ~1s boot finished.

**Fix.** Poll from inside the container or wait long enough before checking. The image itself is fine (372MB, builds, runs, passes `/health`).

**Lesson.** A failing health check can be the *tooling/timing*, not the *application*. On "Up + empty logs + no response," first probe from inside the container to separate the app layer from the network layer.

## Decision — deploy target: Railway vs AWS

On speed alone, Railway/Render (HTTPS in minutes) wins. But the goal here is to *learn DevOps*, so I deliberately chose AWS. The sane path is **App Runner** (container → HTTPS → autoscale, closest to Railway). Lambda (Bun mismatch), raw EC2, and ECS are overkill for this stage, so they're out.
