이 글은 *살아있는 로그*다. 앱 하나(이 프로젝트의 Bun 백엔드)를 로컬 디버깅에서 시작해 컨테이너화 → 클라우드 배포 → CI/CD → 모니터링 → IaC까지 끌고 가는 과정을, **내가 물어본 질문과 막힌 지점, 그 해결**을 하나하나 박아 둔다. 튜토리얼이 아니라 *실제로 겪은 것*만.

## 왜 이렇게 하나

DevOps는 글로 외워지는 게 아니라 *실패를 디버깅하며* 익혀진다. 그래서 진짜 앱 하나를 0→배포까지 깊게 끌고 간다. "마스터"는 과장이지만, 이 하나로 **혼자 서비스를 배포·운영할 수 있는 수준**까지는 확실히 간다 — 그리고 이 기록 자체가 포트폴리오가 된다.

## 에피소드 1 — 폰이 "could not connect": IPv4 vs IPv6 포트 충돌

**증상.** 폰에서 Look 탭이 안 되고, Mac에서 확인하니 `http://localhost:3001/health`가 우리 백엔드가 아니라 **Grafana HTML**을 돌려줬다.

```
backend: ALREADY RUNNING
<!DOCTYPE html> ... <title>Grafana</title> ...
```

**원인 (검증).** `lsof`로 보니 3001 포트에 둘이 동시에 LISTEN 중이었다:

```
bun        6559  ... TCP *:3001 (LISTEN)        # 우리 백엔드 (IPv4)
com.docke 16261  ... TCP [::]:3001 (LISTEN)     # Docker(Grafana 컨테이너) (IPv6)
```

`localhost`는 IPv6(`::1`)를 먼저 잡아서 Docker/Grafana로 갔던 거다. 폰이 `.local:3001`로 붙을 때 IPv6로 풀리면 똑같이 Grafana로 가서 깨졌다.

**해결.** 우리 백엔드를 충돌 없는 포트로 이동: `backend/.env`의 `PORT=3001 → 8787`, `ios-app/project.yml`의 `BackendBaseURL`도 `:8787`로. Grafana(Docker)는 안 건드림.

**배운 것.** 한 포트 번호에 IPv4와 IPv6가 *따로* 바인딩될 수 있다. `localhost`의 해석 순서(보통 IPv6 우선) 때문에 "분명 내 서버 켰는데 남의 게 응답"하는 일이 생긴다. 컨테이너가 호스트 포트를 점유하고 있는지 `lsof -nP -iTCP:<port> -sTCP:LISTEN`로 항상 확인.

## 에피소드 2 — 컨테이너화: Dockerfile과 시크릿 제외

배포 전에 앱을 "어디서든 똑같이 도는 상자"로 포장. 핵심 파일 둘:

- `backend/Dockerfile` — `oven/bun:1-slim` 베이스, 의존성 먼저 복사 후 `bun install`(레이어 캐시), 소스 복사, `ENV PORT=8080`, `CMD ["bun","src/index.ts"]`.
- `backend/.dockerignore` — **`.env`(시크릿)를 이미지에서 제외.** 키는 런타임 환경변수로 주입하지 이미지에 굽지 않는다.

**배운 것.** 이미지 = 얼어붙은 템플릿, 컨테이너 = 그걸 실행한 것, Dockerfile = 굽는 레시피. 의존성 매니페스트를 소스보다 *먼저* 복사하면 소스만 바뀔 때 `install`이 캐시돼 빌드가 빨라진다. 시크릿은 절대 이미지/git에 넣지 않는다.

## 에피소드 3 — "Up인데 health 실패"라는 함정

**증상.** `docker run` 후 호스트에서 `curl /health`가 실패하는데, `docker logs`는 **비어 있고**, `docker ps`는 컨테이너가 **Up**이라고 함. 크래시도 아닌데 응답이 없는 모순.

**원인 (검증).** 컨테이너 *내부*에서 `bun -e 'fetch(...)'`로 찔러보니 정상 응답이 나왔고 로그에도 `Server running at http://localhost:8080`가 찍혀 있었다. 즉 서버는 멀쩡했고, 문제는 *검증 방식*이었다:
- `curl --retry-connrefused`는 "connection refused"에만 재시도한다. 그런데 Docker의 포트 프록시는 호스트 포트를 *즉시* 열어버려서, 앱이 아직 부팅 중이면 "refused"가 아니라 **connection reset**이 난다 → 재시도가 안 걸리고 부팅 1초를 못 기다린 채 실패.

**해결.** 컨테이너 내부에서 폴링하거나 충분히 대기 후 검증. 이미지 자체는 정상(372MB, 빌드·실행·`/health` 모두 통과).

**배운 것.** 헬스체크가 실패해도 *애플리케이션*이 아니라 *검증 도구/타이밍*이 범인일 수 있다. "Up + 빈 로그 + 무응답"이면 먼저 컨테이너 내부에서 직접 찔러봐서 앱과 네트워크 레이어를 분리해 의심하라.

## 의사결정 — 배포 대상: Railway vs AWS

검증 속도만 보면 Railway/Render(분 단위 HTTPS)가 맞다. 하지만 이번 목적은 **DevOps를 *배우는 것***이라, 일부러 AWS를 택했다. 사인 경로는 **App Runner**(컨테이너 → HTTPS → 오토스케일, Railway와 가장 비슷). Lambda(Bun 미스핏)·생 EC2·ECS는 지금 단계엔 과함이라 제외.
